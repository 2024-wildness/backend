Moapin 백엔드 서비스 개발을 위한 PRD(제품 요구사항 정의서)

**1. 목적 및 배경**

Moapin은 사용자가 웹에서 발견하는 다양한 정보(링크, 메모, 사진 등)를 손쉽게 저장, 분류하고, 필요할 때 다시 찾아볼 수 있도록 돕는 개인용 콘텐츠 아카이빙 서비스입니다. 흩어져 있는 정보를 한 곳에 모아 체계적으로 관리하고, 리마인더나 공유 기능을 통해 정보의 활용 가치를 높이는 것을 목표로 합니다. 이 문서는 Moapin 백엔드 시스템의 기능과 요구사항을 정의합니다.

**2. 사용자 스토리 및 핵심 유즈케이스**

*   **역할:** 일반 사용자

*   **사용자 스토리:**
    *   (회원 관리) 나는 회원가입 및 로그인을 통해 나만의 콘텐츠를 안전하게 관리하고 싶다.
    *   (콘텐츠 저장) 나는 웹서핑 중 발견한 유용한 링크나 아이디어를 메모, 사진 형태로 빠르게 저장하고 싶다.
    *   (콘텐츠 분류) 나는 저장한 콘텐츠들을 나만의 기준에 따라 카테고리별로 정리하여 쉽게 찾고 싶다.
    *   (콘텐츠 검색) 나는 내가 저장한 수많은 콘텐츠 중에서 필요한 정보를 키워드로 빠르게 검색하고 싶다.
    *   (리마인더) 나는 중요한 콘텐츠를 잊지 않도록 특정 시간에 알림을 받고 싶다.
    *   (콘텐츠 공유) 나는 내가 저장한 유용한 정보를 다른 사람과 간편하게 공유하고 싶다.
    *   (비밀번호 찾기) 나는 비밀번호를 잊어버렸을 때 이메일 인증을 통해 재설정하고 싶다.

**3. 범위 (Scope)**

*   **포함 (In Scope):**
    *   JWT 기반 회원가입, 로그인, 로그아웃 기능
    *   콘텐츠(링크, 메모, 사진) 생성, 조회, 수정, 삭제 (CRUD)
    *   카테고리 생성, 조회, 수정, 삭제 (CRUD)
    *   콘텐츠에 대한 카테고리 지정 및 변경
    *   키워드 기반 콘텐츠 검색 기능
    *   콘텐츠 기반 리마인더 설정 및 스케줄링
    *   특정 콘텐츠를 공유하기 위한 고유 링크 생성
    *   이메일을 통한 비밀번호 재설정 프로세스

*   **제외 (Out of Scope):**
    *   소셜 로그인 (Google, Kakao 등)
    *   관리자 대시보드
    *   실시간 협업 또는 댓글 기능
    *   콘텐츠 추천 시스템
    *   결제 및 구독 모델

**4. 기능 요구사항**

1.  **회원 인증 시스템**
    *   상세: 사용자는 이메일과 비밀번호로 회원가입하고, 이를 통해 로그인하여 JWT 토큰을 발급받는다.
    *   수용 조건: API 요청 시 발급된 JWT 토큰이 유효해야만 인가된 엔드포인트에 접근할 수 있다. 비밀번호는 암호화되어 저장된다.

2.  **콘텐츠 등록**
    *   상세: 사용자는 링크, 메모, 사진 등 유형에 맞는 데이터를 포함하여 콘텐츠를 생성할 수 있다.
    *   수용 조건: 콘텐츠 생성 API 호출 시, 서버는 데이터를 검증하고 DB에 저장한 후 생성된 콘텐츠의 ID와 정보를 반환한다.

3.  **콘텐츠 조회 및 수정**
    *   상세: 사용자는 자신의 전체 콘텐츠 목록을 조회하거나 특정 콘텐츠의 상세 정보를 볼 수 있다. 또한, 기존 콘텐츠의 제목, 설명 등을 수정할 수 있다.
    *   수용 조건: 사용자는 본인이 소유한 콘텐츠만 조회 및 수정할 수 있어야 한다.

4.  **콘텐츠 삭제**
    *   상세: 사용자는 더 이상 필요 없는 콘텐츠를 삭제할 수 있다.
    *   수용 조건: 콘텐츠 삭제 요청 시, 해당 콘텐츠와 연관된 데이터(리마인더 등)가 함께 삭제되거나 적절히 처리되어야 한다.

5.  **카테고리 관리**
    *   상세: 사용자는 콘텐츠를 분류하기 위한 카테고리를 자유롭게 생성, 수정, 삭제할 수 있다.
    *   수용 조건: 콘텐츠 생성 또는 수정 시 카테고리를 지정할 수 있으며, 카테고리 삭제 시 해당 카테고리에 속한 콘텐츠들은 '미분류' 상태가 된다.

6.  **콘텐츠 검색**
    *   상세: 사용자는 콘텐츠의 제목이나 본문에 포함된 키워드를 통해 원하는 정보를 검색할 수 있다.
    *   수용 조건: 검색 API 호출 시, 검색어와 일치하는 콘텐츠 목록이 정확도 순으로 반환되어야 한다.

7.  **리마인더 설정**
    *   상세: 사용자는 특정 콘텐츠에 대해 원하는 날짜와 시간을 지정하여 리마인더를 설정할 수 있다.
    *   수용 조건: 설정된 시간이 되면, 사용자에게 알림을 보낼 수 있는 기반(예: 이벤트 발행)이 마련되어야 한다.

8.  **콘텐츠 공유**
    *   상세: 사용자는 특정 콘텐츠에 대해 외부에 공유할 수 있는 고유한 URL을 생성할 수 있다.
    *   수용 조건: 생성된 공유 링크에 접근하는 사람은 누구나 해당 콘텐츠의 내용을 조회할 수 있어야 한다.

9.  **비밀번호 재설정**
    *   상세: 사용자가 비밀번호 분실 시, 가입한 이메일로 인증 토큰을 받아 새 비밀번호를 설정할 수 있다.
    *   수용 조건: 인증 토큰은 제한된 시간 동안만 유효해야 하며, 성공적으로 인증된 경우에만 비밀번호 변경이 가능하다.

**5. 비기능 요구사항**

*   **성능:** 핵심 API(콘텐츠 조회/검색)의 평균 응답 시간은 200ms 이내를 목표로 한다. 초당 100건의 동시 요청을 안정적으로 처리할 수 있어야 한다.
*   **보안:** Spring Security를 적용하여 모든 엔드포인트를 보호한다. SQL Injection, XSS 등의 기본적인 웹 취약점을 방어해야 한다. 비밀번호 등 민감 정보는 단방향 암호화(bcrypt)하여 저장한다.
*   **가용성:** 99.9%의 시스템 가용성을 목표로 하며, Docker 기반으로 무중단 배포가 가능해야 한다.
*   **운영:** 모든 API 요청과 비즈니스 로직의 주요 분기점에서 로그를 기록한다. Checkstyle을 통한 코드 컨벤션을 강제하여 코드 품질을 유지한다.

**6. 기술 스택과 제약**

*   **Build Tool:** Gradle 8.5
*   **JDK:** Java 17
*   **Framework:** Spring Boot 3.2.0
*   **주요 라이브러리:**
    *   Spring Web, Spring Security, Spring Data JPA
    *   jjwt (JWT 처리)
    *   Lombok (보일러플레이트 코드 제거)
    *   H2 (테스트용), PostgreSQL (운영용)
    *   QueryDSL (동적 쿼리)
    *   Spring for GraphQL (GraphQL API 지원)
*   **제약사항:** `build.gradle`에 명시된 라이브러리 외 신규 라이브러리 추가 시 아키텍처 검토가 필요하다.

**7. 데이터 모델**

*   **User:** 사용자 정보 (id, email, password)
*   **Category:** 사용자가 생성한 카테고리 (id, name, owner)
*   **Content:** 콘텐츠의 공통 속성 (id, type, title, owner, category). Link, Note, Photo 엔티티가 상속.
    *   **Link:** URL 정보 포함
    *   **Note:** 텍스트 본문 포함
    *   **Photo:** 이미지 저장 경로(URL) 포함
*   **Reminder:** 알림 정보 (id, content, remindAt)
*   **ShareLink:** 공유 링크 정보 (id, content, token, expiresAt)
*   **PasswordResetToken:** 비밀번호 재설정 토큰 정보
*   **주요 관계:** User (1) : (N) Category, User (1) : (N) Content, Category (1) : (N) Content

**8. API 설계**

*   **RESTful API (주요 엔드포인트):**
    *   `POST /api/auth/signup`
    *   `POST /api/auth/login`
    *   `POST /api/auth/password/request`, `POST /api/auth/password/confirm`
    *   `GET, POST /api/categories`
    *   `PUT, DELETE /api/categories/{id}`
    *   `GET, POST /api/contents`
    *   `GET, PUT, DELETE /api/contents/{id}`
    *   `GET /api/search?keyword={query}`
    *   `POST /api/contents/{id}/share-links`
    *   `POST /api/reminders`
*   **GraphQL:** 일부 데이터 조회 기능은 GraphQL 스키마를 통해 제공될 수 있음 (현재 `graphql/` 리소스 존재).

**9. 마일스톤/로드맵**

*   **Phase 1: MVP (기반 구축)**
    *   목표: 핵심 기능(회원, 콘텐츠, 카테고리) 구현
    *   완료 기준: 사용자가 콘텐츠를 저장하고 분류하는 기본 사이클을 완료할 수 있다.

*   **Phase 2: 핵심 기능 확장**
    *   목표: 검색, 리마인더, 공유 기능 추가
    *   완료 기준: 사용자가 저장된 정보를 효과적으로 활용(검색, 알림, 공유)할 수 있다.

*   **Phase 3: 고도화 및 안정화**
    *   목표: 성능 최적화, 테스트 커버리지 확대, 운영 안정성 확보
    *   완료 기준: 검색 성능 개선(예: Elasticsearch 도입), 비기능 요구사항 충족, 모니터링 시스템 연동.

**10. 리스크 및 대응 전략**

*   **리스크:** 대용량 콘텐츠(특히 이미지) 저장 및 처리 비용 증가
    *   **대응:** 이미지 업로드는 클라이언트가 직접 S3 등 외부 스토리지에 업로드하고, 서버는 URL만 관리하는 방식으로 구현. 이미지 리사이징 등 후처리 로직 도입.
*   **리스크:** 검색 기능의 성능 저하
    *   **대응:** 초기에는 DB의 Full-Text Search를 활용하고, 데이터 증가에 따라 Elasticsearch 등 전문 검색 엔진 도입을 검토.
*   **리스크:** 외부 API(이메일 발송 등) 의존성으로 인한 장애
    *   **대응:** 외부 서비스 연동 지점을 인터페이스로 추상화하고, 장애 발생 시를 대비한 Fallback 로직 및 재시도 메커니즘을 구현.
